# 과제 12: 퀵 정렬의 피벗 선택에 따른 성능 비교


## 1. 비교 횟수 계산 기준

세 방법 모두 동일한 **Lomuto partition**을 사용한다. 선택된 피벗을 현재 구간의 마지막 위치로 옮긴 뒤, 각 원소에 대해 다음 비교를 수행한다.

```c
data[j] <= pivot_value
```

이 데이터 값 비교를 1회로 계산한다. 반복문 인덱스 비교나 데이터 이동은 포함하지 않는다.

Median-of-Three에서는 첫 번째, 가운데, 마지막 값 중 중앙값을 고르는 과정에서 발생하는 **데이터 값 비교도 비교 횟수에 포함**하였다.

Random Pivot은 partition이 수행될 때마다 현재 구간에서 새로운 무작위 위치를 선택한다. 데이터 생성용 RNG와 피벗 선택 RNG는 별도로 두어 공정하게 비교하였다.

---

## 2. 실제 측정 결과

| 데이터 크기 | First Pivot | Random Pivot | Median-of-Three | 최소 비교 방식 |
|---:|---:|---:|---:|---|
| 1,000 | 10,608 | 11,472 | 10,812 | First |
| 2,000 | 26,695 | 24,450 | 24,356 | Median-3 |
| 4,000 | 54,000 | 57,217 | 55,646 | First |
| 8,000 | 117,470 | 115,968 | 112,147 | Median-3 |
| 16,000 | 259,555 | 277,668 | 244,087 | Median-3 |
| 20,000 | 323,230 | 333,993 | 311,617 | Median-3 |

모든 데이터 크기에서 `Sorted Verification : Yes`가 출력되어 세 방식 모두 올바르게 오름차순 정렬되었음을 확인하였다.

이번 6개 실험에서 최소 비교 횟수를 기록한 횟수는 다음과 같다.

- First Pivot: **2회**
- Random Pivot: **0회**
- Median-of-Three: **4회**

---

## 3. 데이터 크기 증가에 따른 변화

데이터 크기가 커질수록 세 방법 모두 비교 횟수가 증가한다. 무작위 입력에서는 퀵 정렬이 평균적으로 `O(n log n)`에 가까운 성능을 보이지만, 실제 비교 횟수는 피벗이 각 구간을 얼마나 균형 있게 나누는지에 따라 달라진다.

예를 들어 n=20,000에서:

- First Pivot: **323,230회**
- Random Pivot: **333,993회**
- Median-of-Three: **311,617회**

로 측정되어 이번 실행에서는 Median-of-Three가 가장 적은 비교를 수행하였다.

전체 6개 크기에서 First Pivot은 Median-of-Three의 약 **1.033배**, Random Pivot은 Median-of-Three의 약 **1.056배**의 비교를 수행하였다.

---

## 4. First Pivot 분석

첫 번째 원소를 피벗으로 선택하는 방법은 구현이 가장 단순하고 피벗 선택 자체에 추가적인 데이터 비교가 필요하지 않는다.

이번 실험에서는 n=1,000과 n=4,000에서 First Pivot이 가장 적은 비교 횟수를 기록했다. 이는 입력이 무작위이므로 첫 번째 원소도 우연히 좋은 피벗이 될 수 있고, Median-of-Three는 중앙값을 결정하기 위해 매 partition마다 2~3회의 추가 비교를 수행하기 때문이다.

하지만 First Pivot은 입력 순서에 매우 민감하다. 이미 오름차순 또는 내림차순인 데이터에서 첫 원소를 계속 피벗으로 선택하면 한쪽 부분 배열의 크기가 거의 n-1이 되어 최악의 경우 `O(n^2)`까지 악화될 수 있다.

---

## 5. Random Pivot 분석

Random Pivot은 현재 정렬 구간에서 임의의 위치를 새롭게 선택하므로 특정 입력 순서가 반복적으로 나쁜 피벗을 만들 가능성을 낮춘다.

정렬된 입력처럼 First Pivot에 불리한 데이터에서도 무작위 피벗은 평균적으로 균형 잡힌 분할을 만들 가능성이 높다.

그러나 무작위 선택이 항상 중앙값에 가까운 값을 보장하는 것은 아니다. 이번 seed에서는 Random Pivot이 6개 크기 중 최저 비교 횟수를 기록한 경우가 없었지만, 다른 seed에서는 결과가 달라질 수 있다.

---

## 6. Median-of-Three 분석

Median-of-Three는 첫 번째, 가운데, 마지막 값 세 개를 확인하고 그 중앙값을 피벗으로 사용한다.

장점은 구간의 최솟값이나 최댓값 같은 극단적인 값을 피벗으로 선택할 가능성을 줄이는 것이다. 피벗 선택에 추가 비교가 들어가지만, 더 균형 잡힌 partition을 만들면 전체 재귀 깊이와 이후 비교 횟수를 줄일 수 있다.

이번 실험에서는 6개 중 **4개 크기**에서 Median-of-Three가 가장 적은 비교 횟수를 기록했다. 특히 n=8,000, 16,000, 20,000처럼 데이터가 커질수록 그 장점이 비교적 뚜렷하게 나타났다.

반면 작은 데이터에서는 중앙값을 고르는 추가 비용이 전체 절감량보다 클 수 있어 First Pivot보다 비교 횟수가 더 많게 나타날 수도 있다.

---

## 7. 피벗 선택이 분할 성능에 영향을 미치는 이유

퀵 정렬의 핵심은 한 번의 partition이 배열을 얼마나 균형 있게 나누는가이다.

좋은 피벗이 선택되면:

```text
n -> n/2 + n/2 -> n/4 + n/4 + ...
```

와 같이 재귀 깊이가 작게 유지된다.

반대로 피벗이 계속 최솟값이나 최댓값에 가까우면:

```text
n -> 0 + (n-1) -> 0 + (n-2) -> ...
```

와 같이 매우 불균형한 분할이 반복되고 비교 횟수가 크게 증가한다.

따라서 피벗 선택에 약간의 비용을 쓰더라도 전체적으로 균형 있는 분할을 만들 수 있다면 전체 비교 횟수를 줄일 수 있다.

# 보너스: 재귀적 퀵 정렬과 반복적 퀵 정렬

## 1. 보너스 실행시간 결과

| 데이터 크기 | Recursive (ms) | Iterative (ms) | Iterative / Recursive |
|---:|---:|---:|---:|
| 1,000 | 0.018541 | 0.028663 | 1.546x |
| 2,000 | 0.084779 | 0.098469 | 1.161x |
| 4,000 | 0.113465 | 0.141271 | 1.245x |
| 8,000 | 0.414291 | 0.436679 | 1.054x |
| 16,000 | 0.831836 | 0.875635 | 1.053x |
| 20,000 | 1.115526 | 1.122974 | 1.007x |

이번 실행 환경에서는 모든 데이터 크기에서 재귀형이 약간 더 빠르거나 거의 비슷하게 측정되었다. 특히 n=20,000에서는 재귀형 **1.115526 ms**, 반복형 **1.122974 ms**로 차이가 매우 작았다.

이 결과는 반복형이 무조건 더 빠르다는 의미가 아니다. 반복형은 함수 호출 오버헤드를 피할 수 있지만, 이번 구현에서는 명시적 스택의 `malloc`, push/pop, Range 관리 비용이 추가된다. 반면 Median-of-Three가 비교적 균형 잡힌 분할을 만들어 재귀 깊이가 크지 않아 재귀 호출 비용도 제한적이었다.

실행시간은 CPU, 컴파일러 최적화, 운영체제 스케줄링, 캐시 상태에 따라 달라질 수 있으므로 수치 자체보다 구현 방식에 따른 경향을 보는 것이 적절하다.

---

## 2. 결론

이번 실험에서 퀵 정렬은 동일한 partition을 사용해도 피벗 선택 방법에 따라 비교 횟수가 달라졌다.

First Pivot은 추가 피벗 선택 비용이 없어 단순하고 무작위 데이터에서는 좋은 결과가 나올 수 있지만, 입력 순서에 민감하다.

Random Pivot은 특정 입력 형태에 의한 최악의 분할 위험을 줄이는 장점이 있지만, 매번 중앙에 가까운 값을 보장하지는 않는다.

Median-of-Three는 중앙값을 결정하는 추가 비교가 필요하지만 극단적인 피벗을 피하는 데 도움이 되며, 이번 실험에서는 큰 데이터 크기에서 가장 효과적인 경우가 많았다.

즉 퀵 정렬의 성능 차이는 **피벗 선택 비용 자체와, 그 피벗이 만든 partition의 균형 정도 사이의 trade-off**에서 발생한다.
