# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 1. Heap Sort 구현 및 비교 횟수

Heap Sort는 별도의 힙 배열을 만들지 않고 **입력 배열 자체를 최대 힙으로 사용**한다.

먼저 배열의 마지막 내부 노드부터 `heapify`를 적용하여 최대 힙을 구성하고,
그 다음 루트의 최댓값과 힙의 마지막 원소를 교환한 뒤 힙 크기를 하나 줄여 다시 `heapify`를 수행한다.

비교 횟수에는 자식 노드와 현재 최대값 후보의 **실제 데이터 값 비교만** 포함하였다.

```c
if (data[left] > data[largest])
if (data[right] > data[largest])
```

`left < heap_size` 같은 인덱스/범위 검사는 숫자 비교 횟수에 포함하지 않았다.

Heap Sort는 iterative `heapify`로 구현했기 때문에 재귀 호출 스택이 필요하지 않고 추가 공간은 상수 크기이다.

---

## 2. Merge Sort와 Quick Sort

Merge Sort는 이전 과제와 동일한 재귀적 구현을 사용하며, 두 정렬된 부분 배열을 병합할 때 데이터 값끼리 비교한 횟수를 센다.

Quick Sort도 이전 과제와 동일하게 **Lomuto partition**을 사용한다.
피벗 선택 방식만 다음 세 가지로 바꾼다.

- First Pivot
- Random Pivot
- Median-of-Three

Median-of-Three에서 첫 번째, 가운데, 마지막 값의 중앙값을 결정하기 위한 값 비교도 전체 비교 횟수에 포함하였다.

---

## 3. 실행시간 측정 방법

각 알고리즘의 실행시간은 **같은 원본 데이터에서 50회 실행한 평균값**을 사용하였다.

각 반복에서는:

1. 원본 배열을 작업 배열로 복사
2. 배열 복사가 끝난 뒤 타이머 시작
3. 정렬 실행
4. 정렬 종료 직후 타이머 종료
5. 정렬 결과가 오름차순인지 검증

순서로 측정하였다.

따라서 데이터 생성, 원본 배열 복사, 결과 출력 시간은 실행시간에 포함되지 않는다.

모든 알고리즘에서 C11 `timespec_get()`을 동일하게 사용하였으며 단위는 밀리초(ms)이다.

Random Pivot은 반복 측정마다 같은 pivot RNG seed를 다시 적용하여 동일한 partition 과정을 반복하고 실행시간만 평균내도록 하였다.

## 4. 메모리 사용량 계산 기준

원본 데이터 배열은 모든 알고리즘의 공통 비용이므로 제외하고 **정렬 과정에서 추가로 요구되는 최대 보조 메모리**만 계산하였다.

### Heap Sort

Heap Sort는 입력 배열 자체를 힙으로 사용하며 별도 배열을 할당하지 않는다.
또한 `heapify`를 반복적으로 구현하였다.

따라서 추가 메모리는 `heap_size`, `root`, `largest`, `left`, `right`, `temp`와 같은 보조 정수 상태를 나타내는 `HeapAuxEstimate` 구조체 크기로 계산하였다.
이번 실행 환경에서는 **24 Byte**이다.

즉 Heap Sort의 추가 공간 복잡도는 `O(1)`이다.

### Merge Sort

Merge Sort는 `n`개의 정수를 저장하는 임시 배열과 재귀 호출 스택이 필요하다.

```text
n * sizeof(int)
+ 최대 재귀 깊이 * MergeFrameEstimate 크기
```

로 계산하였다. 따라서 추가 공간은 `O(n)`이다.

### Quick Sort

Quick Sort는 별도 n-sized 배열을 만들지 않고 재귀 호출 스택만 사용한다.

```text
최대 재귀 깊이 * QuickFrameEstimate 크기
```

로 계산하였다.

평균적으로 균형 잡힌 분할이 이루어지면 재귀 깊이는 `O(log n)`이지만,
최악의 피벗 선택이 반복되면 `O(n)`까지 증가할 수 있다.

실제 C 컴파일러가 사용하는 machine stack frame은 ABI와 최적화에 따라 달라질 수 있으므로,
본 과제의 Byte 값은 **알고리즘이 유지해야 하는 논리적 보조 상태를 구조체 크기로 모델링한 계산값**이다.

## 6. 데이터 크기 증가에 따른 비교 횟수

실험 결과 각 데이터 크기에서 가장 적은 비교와 가장 짧은 실행시간은 다음과 같았다.

- n=1,000: 최소 비교 횟수는 **Merge Sort**, 평균 실행시간은 **Quick First**가 가장 짧았다.
- n=2,000: 최소 비교 횟수는 **Merge Sort**, 평균 실행시간은 **Quick First**가 가장 짧았다.
- n=4,000: 최소 비교 횟수는 **Merge Sort**, 평균 실행시간은 **Quick First**가 가장 짧았다.
- n=8,000: 최소 비교 횟수는 **Merge Sort**, 평균 실행시간은 **Quick Median3**가 가장 짧았다.
- n=16,000: 최소 비교 횟수는 **Merge Sort**, 평균 실행시간은 **Quick Median3**가 가장 짧았다.
- n=20,000: 최소 비교 횟수는 **Merge Sort**, 평균 실행시간은 **Quick Median3**가 가장 짧았다.

Heap Sort, Merge Sort, 평균적인 Quick Sort는 모두 `O(n log n)` 계열의 정렬이지만 실제 비교 횟수에는 큰 차이가 나타난다.

Merge Sort는 두 정렬된 부분 배열을 병합할 때 필요한 값 비교만 수행하기 때문에 무작위 데이터에서 비교 횟수가 상대적으로 낮고 일정한 편이다.

Heap Sort는 최대 힙을 처음 구성할 때뿐 아니라 최댓값 하나를 제거할 때마다 힙 속성을 복구해야 한다.
한 번의 `heapify`에서 한 레벨마다 왼쪽/오른쪽 자식과 비교할 수 있어 실제 데이터 비교 횟수가 Merge Sort나 이번 Quick Sort보다 많이 발생하였다.

Quick Sort는 피벗이 배열을 얼마나 균형 있게 나누는지에 따라 비교 횟수가 달라진다.

## 7. 실행시간 차이

비교 횟수가 적다고 실행시간이 항상 가장 짧은 것은 아니다.

### Heap Sort

Heap Sort는 추가 메모리는 매우 작지만 힙 구조상 배열의 서로 떨어진 위치를 반복적으로 접근한다.
이러한 메모리 접근 패턴은 연속적인 배열 구간을 주로 다루는 Merge Sort나 Quick Sort보다 CPU cache 관점에서 불리할 수 있다.
또한 비교와 swap이 반복되어 실제 실행시간이 증가할 수 있다.

### Merge Sort

Merge Sort는 임시 배열을 추가로 사용하지만 병합 과정에서 배열을 순차적으로 읽고 쓰기 때문에 메모리 접근 패턴이 규칙적이다.
반면 각 병합 단계에서 데이터를 임시 배열과 원래 배열 사이로 복사해야 한다.

### Quick Sort

Quick Sort는 원본 작업 배열 안에서 직접 partition을 수행하므로 별도의 큰 임시 배열이 없다.
무작위 데이터에서 균형 잡힌 partition이 형성되면 비교 횟수와 재귀 깊이가 제한되고 cache locality도 비교적 좋다.

따라서 실제 실행시간은 단순 비교 횟수뿐 아니라 **swap 횟수, 데이터 복사, 메모리 접근 패턴, 재귀 구조**에도 영향을 받는다.

## 8. 퀵 정렬 피벗 선택 방식 비교

First Pivot은 구현이 단순하지만 입력 순서에 따라 매우 불균형한 분할을 만들 수 있다.

Random Pivot은 특정 입력 상태가 계속 나쁜 피벗을 만들 위험을 줄이지만, 무작위 선택 자체가 항상 좋은 피벗을 보장하지 않는다.

Median-of-Three는 피벗을 선택할 때 2~3회의 추가 비교가 필요하지만 첫 번째/가운데/마지막 세 값의 중앙값을 사용함으로써 극단적인 피벗을 피하려는 방식이다.

이번 실험에서도 세 Quick Sort의 비교 횟수와 최대 재귀 깊이가 서로 달랐으며,
이는 같은 원본 데이터라도 피벗 선택에 따라 분할 트리의 형태가 달라지기 때문이다.

## 9. n=20,000 직접 비교

n=20,000에서 결과는 다음과 같다.

- Heap Sort: **510,927 comparisons**, 2.457904 ms, **24 B**
- Merge Sort: **261,063 comparisons**, 2.125827 ms, **80,640 B**
- Quick First: **339,525 comparisons**, 1.817650 ms, **1,400 B**
- Quick Random: **356,207 comparisons**, 2.001850 ms, **1,360 B**
- Quick Median3: **317,222 comparisons**, 1.664579 ms, **1,040 B**

비교 횟수만 보면 Merge Sort가 가장 적었고, 추가 메모리는 Heap Sort가 압도적으로 적었다.
실행시간에서는 이번 환경과 데이터에서는 Quick Sort 계열이 강한 결과를 보였다.

## 10. 시간복잡도 및 공간복잡도

| Algorithm | Average Time | Worst Time | Extra Space |
|---|---|---|---|
| Heap Sort | O(n log n) | O(n log n) | O(1) |
| Merge Sort | O(n log n) | O(n log n) | O(n) |
| Quick Sort | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |

Heap Sort는 최악의 경우에도 `O(n log n)`을 보장하면서 `O(1)` 추가 공간을 사용한다는 장점이 있다.

Merge Sort도 최악의 경우 `O(n log n)`이지만 `O(n)`의 임시 배열이 필요하다.

Quick Sort는 평균적으로 빠르고 추가 메모리가 작지만 피벗 선택이 계속 나쁘면 `O(n²)`까지 악화될 수 있다.

## 11. 결론

이번 실험은 세 정렬 알고리즘이 모두 큰 데이터를 효율적으로 정렬할 수 있지만 서로 다른 장단점을 가진다는 것을 보여준다.

- **Heap Sort**는 비교 횟수와 임의 위치 접근이 많아 실제 실행시간이 반드시 가장 빠르지는 않았지만, 추가 메모리가 거의 필요 없고 최악 시간도 `O(n log n)`이라는 장점이 있다.
- **Merge Sort**는 이번 무작위 데이터에서 비교 횟수가 가장 적고 성능이 안정적이었지만 n-sized 임시 배열 때문에 메모리 사용량이 가장 컸다.
- **Quick Sort**는 피벗에 따라 성능 차이가 있었지만 in-place partition과 좋은 평균 성능 덕분에 실제 실행시간에서 매우 경쟁력 있는 결과를 보였다.

따라서 어떤 정렬 알고리즘이 항상 가장 좋다고 단정하기보다는 **메모리 제한, 최악 시간 보장 필요성, 입력 특성, 실제 실행환경**을 함께 고려하여 선택해야 한다.
