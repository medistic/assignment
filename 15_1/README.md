# 과제 15: 퀵 정렬과 AVL 트리 정렬의 성능 비교


## 1. Quick Sort 방식

이전 과제에서 사용한 **Median-of-Three**를 피벗 방식으로 선택하였다.

현재 구간의 첫 번째, 가운데, 마지막 값을 비교하여 중앙값을 피벗으로 선택하고,
모든 분할은 동일한 Lomuto partition을 사용한다.

Quick Sort가 끝난 뒤 배열은 오름차순 상태이므로 삽입 시에는
앞에서부터 삽입 위치를 찾고 뒤 데이터를 한 칸씩 이동한다.

삭제 시에는 앞에서부터 값을 선형 탐색하고,
찾으면 그 뒤의 값을 한 칸씩 앞으로 이동한다.

중복 값은 그대로 허용하며 삭제 요청 한 번당 한 개만 제거한다.

---

## 2. AVL Tree 방식

원본 데이터를 처음부터 AVL 트리에 하나씩 삽입한다.

각 노드는 다음 정보를 가진다.

```text
key
count
height
left pointer
right pointer
```

동일한 `key`가 다시 들어오면 새 노드를 만들지 않고 `count`를 증가시킨다.

삭제도 `count > 1`이면 count만 하나 감소시키고,
마지막 한 개를 삭제할 때만 실제 노드를 제거한다.

구조 변경 후에는 balance factor를 계산해 필요한 회전을 수행한다.

회전에서 포인터 연결만 바뀌는 경우는 과제 명세에 따라 데이터 이동 횟수에 포함하지 않았다.

---

## 3. 비교 횟수 측정 기준

### Quick + 배열

다음을 포함하였다.

- Median-of-Three에서 세 데이터 값을 비교한 횟수
- partition에서 배열 값과 pivot 값을 비교한 횟수
- 정렬 배열 삽입 위치를 찾기 위해 확인한 데이터 값
- 삭제할 값을 찾기 위해 확인한 데이터 값

반복문 인덱스와 종료 조건은 제외하였다.

### AVL

트리에서 삽입 또는 삭제 키와 현재 노드의 `key`를 확인할 때마다
**논리적 key 비교 1회**로 계산하였다.

AVL의 height 비교, balance factor 확인, 회전 조건 등
데이터 key와 무관한 제어 비교는 제외하였다.

---

## 4. 데이터 이동 횟수 측정 기준

### Quick + 배열

데이터 값을 다른 저장 위치나 임시 변수에 복사하는 동작을 계산하였다.

- Quick Sort swap: 3회
- Median-of-Three 값을 임시 변수에 복사
- pivot 값을 임시 변수에 저장
- 배열 삽입 시 뒤로 한 칸씩 이동
- 삽입 값 최종 저장
- 삭제 후 뒤 데이터를 앞으로 이동

원본 데이터를 실험용 배열에 복사하는 과정은 정렬 시작 전 준비 단계이므로 제외하였다.

### AVL

- 새 노드의 `key` 필드에 값을 저장하는 경우
- 두 자식 노드를 가진 노드 삭제 시 successor key를 복사하는 경우

만 데이터 이동으로 계산하였다.

포인터 연결 변경, height 변경, duplicate `count` 변경은 데이터 key 이동이 아니므로 제외하였다.

---

## 5. 실행시간 측정 기준

두 방식 모두 다음 구간을 측정한다.

### Quick 방식

```text
Quick Sort 시작
→ 모든 삽입/삭제 완료
```

### AVL 방식

```text
원본 데이터의 첫 AVL 삽입 시작
→ 모든 삽입/삭제 완료
```

원본 데이터 생성, 연산 목록 생성, 배열 복사, 결과 검증, 출력은 타이머 밖에서 수행하였다.

측정 잡음을 줄이기 위해 같은 입력/연산으로 **5회 실행한 평균**을 사용하였다.
실행 순서에 따른 CPU/cache 편향을 줄이기 위해 Quick과 AVL의 실행 순서도 반복마다 번갈아 적용하였다.

---

## 6. 메모리 계산 기준

원본 입력 배열과 실험용 연산 목록은 두 방식에 공통으로 필요한 입력이므로 제외하였다.

### Quick + 배열

실제로 할당한 정렬 배열의 최대 용량은:

```text
n + operation_count
```

이다. 모든 연산이 삽입일 수도 있으므로 이 크기를 미리 확보하였다.

여기에 Quick Sort의 최대 재귀 깊이와 논리적 재귀 프레임 크기를 더하였다.

```text
(n + operation_count) * sizeof(int)
+ max_quick_depth * sizeof(QuickFrameEstimate)
```

### AVL

실험 중 동시에 존재했던 최대 고유 노드 수를 기록하고 다음과 같이 계산하였다.

```text
sizeof(AVLTree)
+ peak_unique_nodes * sizeof(AVLNode)
+ max_avl_depth * sizeof(AVLFrameEstimate)
```

실제 C compiler의 machine stack frame 크기는 ABI와 최적화 설정에 따라 다르므로,
재귀 stack 부분은 각 호출에서 유지해야 하는 논리적 상태를 구조체로 모델링한 계산값이다.

## 8. 총 수행시간 분석

실행시간 결과는 다음과 같다.

- n=1,000: Quick 0.075764 ms, AVL 0.100841 ms → Quick이 약 1.33배 빠름
- n=2,000: Quick 0.293044 ms, AVL 0.228882 ms → AVL이 약 1.28배 빠름
- n=4,000: Quick 0.938526 ms, AVL 0.542303 ms → AVL이 약 1.73배 빠름
- n=8,000: Quick 3.731237 ms, AVL 1.227971 ms → AVL이 약 3.04배 빠름
- n=16,000: Quick 13.943638 ms, AVL 3.118583 ms → AVL이 약 4.47배 빠름
- n=20,000: Quick 20.747566 ms, AVL 3.773144 ms → AVL이 약 5.50배 빠름

n=1,000에서는 Quick 방식이 조금 빨랐다.
작은 데이터에서는 AVL 노드 동적 할당, height 갱신, 회전 등의 고정 오버헤드가 상대적으로 크게 보이기 때문이다.

하지만 n이 커지면서 AVL이 빠르게 유리해졌다.

n=20,000에서는:

- Quick + 배열: **20.747566 ms**
- AVL Tree: **3.773144 ms**

로, AVL이 약 **5.50배 빠르게** 측정되었다.

이 실험은 최초 정렬뿐 아니라 이후 `n/5`회의 삽입·삭제까지 포함한다.
따라서 반복적인 데이터 변경 비용이 전체 시간에 크게 반영된다.

---

## 9. 비교 횟수 분석

n=20,000에서:

- Quick + 배열: **63,106,070회**
- AVL Tree: **320,470회**

로 Quick 방식이 약 **196.92배** 많은 데이터 비교를 수행하였다.

정렬 배열은 삽입 위치나 삭제 대상을 찾을 때 앞에서부터 선형으로 탐색한다.
데이터가 커질수록 한 연산에서 확인해야 하는 원소 수가 증가한다.

특히 삭제 대상이 존재하지 않는 경우 정렬 배열은 많은 원소를 끝까지 확인할 수 있지만,
AVL은 루트에서 한쪽 자식으로만 내려가므로 트리 높이에 비례하는 경로만 확인한다.

AVL은 균형을 유지하므로 일반적으로 삽입과 삭제 탐색이 `O(log n)` 범위에서 수행된다.

---

## 10. 데이터 이동 횟수 분석

n=20,000에서:

- Quick + 배열: **21,614,562회**
- AVL Tree: **21,784회**

로 Quick + 배열이 약 **992.22배** 많은 데이터 이동을 기록하였다.

정렬 배열에 중간 위치로 값을 삽입하면 뒤의 많은 데이터를 한 칸씩 이동해야 한다.
삭제 역시 삭제 위치 뒤의 데이터를 앞으로 당겨야 한다.

반면 AVL은 노드의 물리적인 배열 위치를 이동시키지 않는다.
대부분의 구조 변경은 포인터 연결과 회전으로 해결되므로,
과제의 데이터 이동 기준에서는 이동 횟수가 매우 작게 나타났다.

이 차이가 반복적인 삽입·삭제가 있는 환경에서 AVL의 중요한 장점이다.

---

## 11. 메모리 사용량 분석

n=20,000에서:

- Quick + 배열: **97,000 Bytes**
- AVL Tree: **696,344 Bytes**

로 AVL이 약 **7.18배** 많은 추가 메모리를 사용하였다.

배열은 각 데이터가 `int` 하나만 필요하고 연속된 메모리에 저장된다.

AVL 노드는 key 외에도:

- duplicate count
- height
- left pointer
- right pointer

를 각각 저장해야 한다.

따라서 AVL은 삽입·삭제 성능을 얻는 대신 더 큰 메모리 비용을 지불한다.

---

## 12. 데이터 크기 증가에 따른 성능 변화

정렬 배열에서 삽입과 삭제는 탐색 및 원소 이동 때문에 한 번의 연산이 `O(n)`이 될 수 있다.

이 과제에서는 연산 횟수 자체도 `0.2n`으로 증가한다.
따라서 n이 커질수록 삽입·삭제 단계의 총 비용이 매우 빠르게 커진다.

반면 AVL의 삽입과 삭제는 균형 높이를 유지하여 일반적으로 `O(log n)`이고,
연산 횟수가 증가하더라도 배열보다 완만하게 비용이 증가한다.

실제 결과에서도 n이 커질수록 Quick + 정렬 배열과 AVL 사이의
비교 횟수와 데이터 이동 횟수 차이가 크게 벌어졌다.

---

## 13. 구조적 차이

### Quick Sort + 정렬 배열

장점:

- 연속 메모리이므로 저장 공간 효율이 높음
- cache locality가 좋음
- 최초 정렬 후 순차 접근이 매우 빠름
- 구조가 단순함

단점:

- 중간 삽입 시 많은 데이터 이동 발생
- 삭제 후 빈 위치를 메우기 위해 많은 데이터 이동 발생
- 본 과제처럼 선형 탐색을 사용하면 삽입/삭제 탐색도 `O(n)`

### AVL Tree

장점:

- 항상 균형에 가까운 높이를 유지
- 삽입/삭제 탐색이 일반적으로 `O(log n)`
- 회전이 포인터 변경 중심이므로 실제 key 이동이 적음
- 데이터 변경이 반복되는 환경에 적합

단점:

- 노드마다 여러 metadata와 pointer가 필요
- 메모리 사용량이 큼
- 동적 메모리 할당 및 회전 관리가 필요
- 구현이 배열보다 복잡함

---

## 14. 결론

이번 실험에서는 정렬 한 번으로 끝나는 상황이 아니라,
정렬 후 데이터 크기의 20%만큼 삽입과 삭제를 반복하였다.

작은 n에서는 배열 기반 Quick 방식도 충분히 빠르고 메모리 효율이 높았다.
하지만 n이 커지면 선형 탐색과 원소 이동이 반복되어 전체 비용이 크게 증가하였다.

AVL은 더 많은 메모리를 사용하지만,
균형 트리 구조 덕분에 데이터가 커져도 삽입과 삭제 시 확인해야 하는 노드 수가 상대적으로 적고,
포인터 변경을 통해 구조를 조정하기 때문에 데이터 이동도 매우 적었다.

따라서:

- **정렬 후 데이터 변경이 거의 없고 메모리 효율/순차 접근이 중요하면 배열 + Quick Sort**
- **정렬 상태를 유지하면서 삽입·삭제가 지속적으로 반복되면 AVL Tree**

가 더 적합하다.

이번 실험 결과는 반복적인 삽입·삭제 환경에서는 AVL의 추가 메모리 비용을 감수하더라도
전체 수행시간과 데이터 이동 측면에서 큰 이점을 얻을 수 있음을 보여준다.
